<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → Supabase Realtime (WebSocket) | Authenticated supabase-js client opens a WebSocket to Supabase Realtime; postgres_changes events flow back |
| component → service layer | FSD boundary — components must not call supabase directly; services own all DB+Realtime access |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-03 | Elevation of Privilege / Architectural | Direct `supabase` import in OrdersRegistry/PermitsRegistry/PrescriptionsRegistry.jsx | mitigate | Move all `supabase.channel(...)` calls into the corresponding service file; remove the static `import { supabase }` from each .jsx component. The Supabase client is a singleton (per CLAUDE.md) — moving the call site does not change auth context or RLS enforcement, but it eliminates the FSD violation that allowed components to bypass the service layer for any future Supabase call. Acceptance grep proves the supabase import is gone from all 3 components. |
| T-1-03b | Tampering | Realtime channel name drift could break server-side filters/notifications | mitigate | Service functions use `REALTIME_CHANNELS.X` from the existing shared constants module — same source the components used. No string is hardcoded in services. Acceptance grep verifies the constant file is unchanged and each service references it. |
| T-1-03c | Denial of Service | Subscription leak if component unmounts without cleanup | mitigate | Each refactored useEffect returns a cleanup that calls `channel.unsubscribe()`. The service returns the RealtimeChannel directly so the component retains the reference for cleanup — same pattern as the original code, just one indirection deeper. |
</threat_model>
